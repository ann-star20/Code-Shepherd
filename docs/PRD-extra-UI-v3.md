# 🛠️ 기능 수정 및 추가개발 지침서

## 1. UI 레이아웃 및 컴포넌트 구조 변경

**목적:** 화면 복잡도를 낮추고, 지식화 대기 중인 URL에 사용자의 시선이 집중되도록 레이아웃을 전면 개편합니다.

### 1-1. 컬럼 배치 및 노출 조건 수정

* **[AS-IS]:** 2바디(Left/Right Column) 형태의 화면 구조
* **[TO-BE]:** * 기존 `/* ══ LEFT COLUMN ══ */` 컴포넌트는 전체 **숨김(Unmount 또는 `display: none`) 처리**합니다.
* `/* URL 대기열 */` 컴포넌트를 `/* ══ RIGHT COLUMN ══ */` 내의 최상단(가장 첫 번째 영역)으로 배치 이동합니다.


* **개발 가이드:** 레이아웃 플렉스 박스 또는 그리드 시스템에서 Left 영역의 그리드 비율을 `0`으로 만들고 Right 영역이 화면 전체(`width: 100%`)를 차지하도록 스타일을 조정합니다.

## 2. [파이프라인 시작 전 단계] 중복 문서 검증 가드레일 (Etag 체크)

**목적:** 이미 분석 및 지식화가 완료된 동일 버전의 문서를 중복 처리하여 리소스를 낭비하는 것을 방지합니다.

### 2-1. 메커니즘 흐름 (`runPipelineStart` 진입 직후)

1. 사용자가 입력한 각 링크(URL)에 대해, 시스템은 먼저 고유 식별자(`doc_id`)와 현재 웹상의 콘텐츠 검증 지문(`etag`)을 획득합니다.
2. `documents` 테이블(또는 캐시 레이어)에서 **동일한 `doc_id`와 동일한 `etag`를 가진 레코드가 이미 존재하는지** 조회합니다.
3. **중복 데이터가 존재할 경우 즉시 Return** 처리하고 아래의 팝업을 노출합니다.

### 2-2. 예외 처리 UI (얼럿/팝업)

* **메시지 스펙:** `"{링크주소}는 이미 지식화된 문서입니다."`
* **인터랙션:** 사용자가 **"확인"** 버튼을 누르면, 해당 링크만 대기열에서 제외(Filter-out)하고, 나머지 입력된 다음 링크들의 파이프라인 작업을 끊김 없이 연속적으로 진행합니다.

## 3. [파이프라인 진행 단계] 신뢰도 미달 문서에 대한 HITL(Human-In-The-Loop) 개입

**목적:** AI의 사전 분석(Prescan) 결과가 불안정하거나 데이터가 부족할 때, 개발자(사람)가 직접 검증하고 메타데이터를 보정하는 안전장치를 마련합니다.

### 3-1. HITL 트리거 조건 (`runPipelineStart` 내부)

각 링크가 `/documents/${docId}/prescan` 단계를 거친 후, 다음 3가지 조건 중 하나라도 충족되면 파이프라인을 일시 중단하고 **HITL 팝업**을 띄웁니다.

* 조건 A: `/prescan` 결과(Response 데이터) 자체가 존재하지 않는 경우
* 조건 B: 분석 결과 내 `infer_confidence`(추론 신뢰도) 속성 값이 누락된 경우
* 조건 C: `infer_confidence` 값이 존재하지만 **`0.8` 미만**인 경우 ($infer\_confidence < 0.8$)

### 3-2. HITL 팝업 UI/UX 스펙

* **데이터 노출:** * 대상 링크별로 현재 추론된 `framework`와 `lang` 값을 보여줍니다. (만약 분석 결과가 없다면 **빈값/Blank** 처리)
* **컴포넌트 제어:** * `framework` 변경 영역은 셀렉트 박스(Select Box)로 구현합니다.
* 이 셀렉트 박스의 Options 데이터는 데이터베이스의 **`framework_metadata` 테이블**에 등록된 마스터 데이터를 바인딩하여 컴포넌트를 동적으로 구성합니다.
* 사용자는 셀렉트 박스에서 마스터 데이터를 선택하거나, 필요시 직접 텍스트를 입력(Editable Select)하여 최종 적용할 수 있어야 합니다.



### 3-3. 작업 취소 프로세스 (Rollback)

* 팝업 내에 **[작업 취소하기]** 버튼을 배치합니다.
* 사용자가 취소를 선택할 경우, 해당 파이프라인 트랜잭션을 중단하고 데이터 정리를 위해 `documents` 테이블에서 해당 `doc_id`를 가진 임시 레코드를 즉시 삭제(Hard Delete 또는 상태 변경)해야 합니다.

## 4. [예외/실패 단계] 크롤링 불가 링크에 대한 로깅 및 UI 피드백

**목적:** 유효하지 않은 URL이거나 네트워크/보안 상의 이유로 크롤러가 접근할 수 없는 경우, 시스템 로그를 남기고 유저에게 실패 원인을 직관적으로 제공합니다.

### 4-1. DB 로깅 아키텍처 (`pipeline_logs` 테이블)

크롤링 실패(네트워크 에러, 404, 403, 파싱 실패 등) 감지 시, `pipeline_logs` 테이블에 아래의 스펙으로 인서트(Insert) 쿼리를 수행합니다.

| 컬럼명 (Column) | 입력 값 (Value) | 설명 |
| --- | --- | --- |
| **`agent`** | `'Crawler'` | 실패 주체를 명시 |
| **`level`** | `'ERROR'` | 로그 레벨 강제 |
| **`message`** | `"{구체적인 실패 원인}"` | 예: `403 Forbidden`, `Invalid URL Format`, `Timeout` 등 실데이터 로깅 |

### 4-2. 프론트엔드 UI 대기열 피드백

* **상태 표시:** `/* URL 대기열 */` 영역 내에서 문제가 발생한 해당 링크 라인의 가장 오른쪽(Right-end)에 **"실패"** 텍스트(또는 빨간색 배지 코딩)를 출력합니다.
* **툴팁(Tooltip) 인터랙션:** 사용자가 해당 "실패" 문구에 마우스를 올리면(Hover), `pipeline_logs`에 저장된 **구체적인 실패 원인 메시지가 툴팁 형태로 팝업**되도록 구현합니다.
