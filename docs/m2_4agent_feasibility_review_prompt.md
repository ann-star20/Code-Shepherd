# Claude Code 검토 요청 프롬프트: m2 내부 4개 기능 오케스트레이션 가능성 확인

## 목적

현재 전체 설계 변경 가능성을 검토하고 싶다.  
아직 구현하지 말고, 먼저 코드와 현재 구조를 분석해서 가능한지 판단해줘.

## 배경

기존 설계는 m1이 중앙 오케스트레이터로 m2, m3를 병렬 호출하고, 그 결과를 m4에 전달하는 구조였다.

하지만 현재 방향은 m2 내부에 mini-orchestrator를 두고, m2가 자체적으로 m1~m4 end-to-end 흐름을 수행하는 구조로 바뀌었다.

## 내가 알고 싶은 것

현재 m2 안에서 기존 m2 기능 2개만 실행하는 구조가 아니라, m3가 구현한 테스트 검증/성능 분석 기능까지 함께 연결해서 총 4개 기능을 m2 orchestrator에서 조율할 수 있는지 검토해줘.

## 검토 대상 기능

1. StaticAnalysisAgent - 기존 m2 정적분석 기능
2. SecurityScanAgent - 기존 m2 보안스캔 기능
3. TestVerificationAgent - 기존 m3 테스트 검증 기능
4. PerformanceAgent - 기존 m3 성능 분석 기능

## 중요한 조건

- 아직 구현하지 마라.
- 먼저 가능한 구조인지 분석만 해라.
- 팀원들과 공유하는 문서나 공통 계약 문서는 절대 수정하지 마라.
- 기존 m2 정적분석/보안분석 구현은 최대한 보존해야 한다.
- 기존 `/analyze/static`, `/analyze/security` 엔드포인트는 삭제하거나 깨면 안 된다.
- m3 코드를 m2에 복붙하는 방식은 피하고 싶다.
- 가능하다면 m2 내부에 `m3_client.py` 같은 client 계층을 두고 m3 기능을 호출하는 방식이 적절한지 검토해줘.
- m3 서비스가 없거나 `M3_BASE_URL`이 없을 때 graceful fallback으로 m2의 2개 결과만 m4에 전달할 수 있는지도 검토해줘.
- m4가 4개의 `AgentResult`를 `analysis_results` 배열로 받을 수 있는 구조인지 확인해줘.
- 현재 코드 기준으로 DTO/계약/엔드포인트/응답 형식 충돌이 있는지 확인해줘.

## 답변 형식

검토 후 아래 형식으로 답변해줘.

### 1. 결론

- 가능한지 / 위험한지 / 불가능한지 명확히 말해줘.

### 2. 추천 구조

- m2가 4개 기능을 직접 소유하는 방식이 맞는지
- 아니면 m2는 기존 2개 기능만 직접 실행하고 m3의 2개 기능은 client로 호출하는 방식이 맞는지 판단해줘.

### 3. 현재 코드 기준 확인할 파일

- 어떤 파일들을 봐야 하는지 목록으로 알려줘.
- 예:
  - `backend/m2/app/main.py`
  - `backend/m2/app/analyzer.py`
  - `backend/m2/app/contract.py`
  - `backend/m3` 관련 파일
  - m4 요청 DTO
  - m4 review/generate 관련 엔드포인트

### 4. 충돌 가능성

아래 항목별로 충돌 가능성을 확인해줘.

- 기존 m2 계약과 충돌하는 부분
- m3 계약과 충돌하는 부분
- m4 입력 형식과 충돌하는 부분
- 공유 문서를 수정해야만 가능한 부분이 있는지
- 기존 테스트가 깨질 가능성이 있는지

### 5. 구현한다면 필요한 최소 변경 파일

아래를 구분해서 알려줘.

- m2 안에서 추가해야 할 파일
- m2 안에서 수정해야 할 파일
- m3 수정이 필요한지 여부
- m4 수정이 필요한지 여부
- 공유 문서 수정 없이 가능한지 여부

### 6. 안전한 구현 순서

기존 m2 정적분석/보안분석을 보존하면서 점진적으로 구현하는 순서로 알려줘.

### 7. 최종 판단

아래 세 가지 중 하나로 결론을 내려줘.

- A. m2 내부에서 4개 기능 orchestration 가능하며, m3는 client로 호출하는 방식 추천
- B. 가능은 하지만 m4 DTO나 계약 수정이 필요해서 팀 합의가 먼저 필요
- C. 현재 구조상 위험하므로 m2는 기존 2개 기능만 담당하는 것이 좋음

## 매우 중요한 제한

지금은 구현 금지.  
코드 수정하지 말고 feasibility review만 해라.

공유 문서 수정 금지.  
공통 계약 문서 수정 금지.  
기존 m2 정적분석/보안분석 로직 삭제 금지.
