# SESSION C (계획) — 레포 등록 시 "한방에": 웹훅 + 토큰 자동화 (Stage 2)

> 목표(사용자 플로우 2단계): **데모레포를 웹사이트에서 등록할 때, 지금 손으로 하는 셋업이 자동으로 끝나게.**
> 지금은 사람이 일일이: ① ngrok 켜서 주소 복사 ② GitHub 웹훅 수동 등록 ③ GITHUB_TOKEN 수동 세팅.
> → 이걸 **등록 한 번으로** 처리. (핵심 결과물 SESSION_4·5 끝난 뒤 착수 권장)

> ⚠️ 이건 아직 "계획"이다. 접근법(아래 A/B) 하나를 정하면 그때 실행 세션으로 바꾼다.

---

## 지금 수동인 것 3개 → 자동화 대상
| # | 지금(수동) | 자동화 후 |
|---|---|---|
| 1 | GitHub 레포 Settings에서 웹훅 직접 추가 | 레포 등록 시 **웹훅 자동 생성** (GitHub API) |
| 2 | ★ **GITHUB_TOKEN 수동으로 .env에 넣기** | **토큰 자동 획득**(아래) → 코멘트 게시·웹훅 생성에 사용 |
| 3 | ngrok 켜서 공개주소 복사 → 웹훅 URL에 넣기 | **공개 URL 자동**(배포 or GitHub App이 배달) |

---

## ★ 토큰 자동화 (이번에 추가 요청한 부분)
지금은 코멘트 게시용 `GITHUB_TOKEN`을 사람이 webhook-gateway/.env에 넣어 재사용 중.
자동화하면 **사용자가 토큰을 따로 만들 필요 없이**, 로그인/설치 과정에서 시스템이 알아서 권한 있는 토큰을 받아 쓴다.
이 토큰 하나로 두 가지에 씀: **(a) 웹훅 생성** (admin:repo_hook) **(b) PR 코멘트 게시** (repo/pull_request write).

---

## 접근법 2가지 (하나 선택)

### A. GitHub App (권장 — 운영/확장에 정석)
- 사용자가 **App을 레포에 설치**하면 → GitHub이 **웹훅을 자동 등록**해주고, **설치 토큰(installation token)** 을 발급(짧은 수명·레포 한정·안전).
- 그 토큰으로 코멘트 게시. **사용자가 토큰을 직접 만들 일 없음.**
- 장점: 가장 자동·안전(최소 권한·자동 만료). 단점: App 등록 + 설치 + JWT→설치토큰 교환 플로우 구현 필요(초기 셋업 좀 있음).

### B. OAuth 스코프 확장 (빠른 길)
- 지금 GitHub 로그인(OAuth)에 **`repo` + `admin:repo_hook` 스코프 추가**로 요청 → 로그인 시 받은 **access_token을 저장**.
- 레포 등록 시 그 토큰으로 **웹훅 생성** + **코멘트 게시**.
- 장점: 기존 OAuth 흐름 재사용이라 빠름. 단점: 사용자 토큰을 저장해야 함(보안 고려), 권한이 넓음(사용자 전체 repo).
- ⚠️ 현재 api-core는 OAuth access_token을 **저장 안 하고 버림** + 스코프도 좁음 → 둘 다 바꿔야 함.

## 만들 것 (접근법 무관 공통 + 영역)
1. **토큰 확보** — A: App 설치토큰 교환 / B: OAuth 스코프 확장 + 토큰 저장 (api-core auth)
2. **웹훅 자동 생성** — 레포 등록 시 `POST /repos/{owner}/{repo}/hooks` 호출(secret·이벤트 PR·URL 자동) (api-core)
3. **공개 URL** — 백엔드 배포(고정 공개주소) 또는 App 배달 사용 (인프라). 로컬만이면 ngrok 자동기동 스크립트로 대체 가능
4. **게시에 토큰 연결** — m3 github_poster가 수동 GITHUB_TOKEN 대신 **확보한 토큰**을 쓰게 (m3 — 작은 변경)

> 영역: 주로 **api-core(인증·웹훅생성·토큰저장)** + **frontend(등록 UI)** + **m3(게시 토큰 연결)** + **인프라(배포/App)**.
> → 네 m3만의 일이 아니라 **팀 협업 필요**(특히 api-core·인프라). 그래서 핵심(4·5) 먼저, 이건 그 뒤.

## 결정 필요 (착수 전)
1. **A(GitHub App) vs B(OAuth 확장)** — 운영까지 보면 A, 빨리 데모면 B.
2. **공개 URL**: 백엔드를 어디 배포? (배포되면 ngrok 자체가 불필요) 아니면 당분간 로컬+ngrok 자동화?
3. **누가 api-core/인프라 담당** — 이 부분은 m3 밖이라 담당 팀원과 협의.
