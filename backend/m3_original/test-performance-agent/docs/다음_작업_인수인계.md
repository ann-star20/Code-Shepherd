## 3. 앞으로 할 일 ② — 사내 컨벤션 RAG (오늘 논의한 핵심)

**질문이었던 것**: "테스트 커버리지·성능 평가 기준은 누가 정하나? 사내 문서로? 바뀌면 따라 바뀌나?"

**결론 (이미 답 나옴)**:
- 기준은 **업계 표준(80% 등) + 사내 컨벤션** 둘 다. 80%는 법이 아니라 흔한 기본값, 진짜는 **사내 규칙 우선**.
- 사내 기준이 바뀌면 평가도 바뀌게 = **RAG로 가능**.

### ⭐ RAG 상세 설계는 `RAG_설계서.md` 가 정본 — 거기 보라!

> 이 §3은 요약일 뿐. **실제 설계·구현 청사진·4대 위험 해결책·TDD 플랜은 전부 `RAG_설계서.md`** 에.

**핵심만 (정본 요약)**:
- 정량 기준(커버리지% 등) → **config 구조화** (RAG 자연어 파싱 ❌, 깨지면 PR판정 재앙)
- 정성 가이드(설명·패턴) → **RAG로 코멘트 인용에만**
- 검색·임베딩 → **Dev1 KMS API 호출** (chunk_embeddings 직접 SELECT ❌, 임베딩 직접 ❌)
- 검색 쿼리 → 이슈 **message 통째로** (짧은 키워드 ❌)
- 하네스 → 표준 DTO·레지스트리는 **기존 게이트웨이 재활용**, RAG는 독립 미들웨어, 전부 Mock 고립 테스트
- 시작 메시지: RAG_설계서.md §10 복붙

## 3.5 Dev4 요청 — scan_issues 이슈 키워드 구조화 ⭐ (우선)

### 배경: Dev4가 왜 원하나
Dev4 = 평가 + 코멘트 작성 + 패턴 집계(Dev5 연계). 그래서 이슈를 두 목적에 맞게:
- **① 사람이 읽기 쉽게** (코멘트에 "커버리지 미충족 26.7%" 깔끔히)
- **② 기계가 집계하기 쉽게** ("이 신입은 '함수 누락' 반복" 같은 통계)

→ Dev4 원본 예시는 형식이 들쭉날쭉(어떤 건 수치, 어떤 건 설명). **3개 컬럼으로 정규화**하면 Dev4가 훨씬 잘 씀.

### 설계 — scan_issues에 컬럼 3개 추가

| 컬럼 | 의미 | 채우는 규칙 |
|---|---|---|
| `keyword` | **대분류** (고정값, 집계·통계 키) | 탐지기별 정해진 한글 라벨 |
| `sub_keyword` | **세부 대상** (어디서/무엇이) | 함수명·파일위치 등 |
| `metric_value` | **수치** (있을 때만, 없으면 NULL) | "26.7%", "쿼리 87회" 등 |

### 탐지기별 채우는 값 (확정안)

| rule_id | keyword (대분류) | sub_keyword (세부) | metric_value (수치) |
|---|---|---|---|
| TEST-001 (커버리지) | `커버리지 미충족` | `(전체)` 또는 파일 | `26.7%` (실측 라인%) |
| TEST-004 (테스트 누락) | `테스트 누락` | 함수명 (`load_cart_items`) | NULL |
| TEST-003 (엣지케이스) | `엣지케이스 누락` | 함수명 | NULL |
| PERF-002 (N+1) | `N+1 쿼리` | 위치 (`src/cart.py:8`) | (향후 A2: 쿼리횟수) |
| PERF-001 (복잡도) | `시간복잡도` | `O(n^2)` + 함수명 | NULL |
| PERF-003 (메모리) | `메모리 누수` | 위치 | NULL |

> **설계 포인트 (Dev4 친화)**:
> - `keyword`는 **고정 한글 라벨** → Dev4가 `GROUP BY keyword`로 바로 통계 가능 ("N+1 쿼리 이번 달 8회").
> - `sub_keyword`는 **구체적 대상** → 코멘트에 "load_cart_items 함수에 테스트 없음" 자연스럽게.
> - `metric_value`는 **수치 분리** → Dev4가 "26.7%"를 숫자로 따로 쓰거나 성장그래프에 활용.
> - 셋 다 채우는 건 **탐지기 안에서** (Issue 생성 시). 없는 값은 빈 문자열/NULL로 정직하게.

### 할 일
1. `contracts.py`의 `Issue` 모델에 `keyword`, `sub_keyword`, `metric_value` 필드 추가 (기본 빈값).
2. 각 탐지기가 Issue 만들 때 위 표대로 채우기.
3. `scan_issues` 테이블에 컬럼 3개 추가 (공유 DB → **Dev2/팀 합의 후**). 합의 전엔 코드만 준비.
4. persist INSERT에 3컬럼 포함.
5. Dev4에게 "이 3컬럼으로 정규화했다" 공유 (원본 2칸 요청 → 3칸으로 개선 제안).
