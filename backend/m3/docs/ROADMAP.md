## 🌟 v2-1. 실시간 trace 표시 (최우선 — 데모 임팩트)

### 왜 필요한가 (배경)
현재 프론트는 **polling 방식**이다. PR을 올리면 → 백엔드가 분석(수십 초) → 완료된 다음에야 결과를 한 번에 가져온다. 그래서 사용자가 PR을 올리고 웹사이트로 돌아오면 **완료될 때까지 빈 화면을 기다려야** 한다. 분석이 돌고 있는지조차 안 보인다.

지금도 trace 타임라인(⓪→⑤, 각 단계 소요시간)은 결과에 포함돼 있고 프론트에서 렌더된다 — 단 **끝난 뒤에 한 번에** 보인다. (참고: `RAG 파이프라인 실행 흐름` 토글에 ⓪입력수집→①개념추출→②KMS검색→③충분성판단→④규칙판정→⑤코멘트생성이 각 ms와 함께 표시됨)

### 목표 (무엇을 만드는가)
PR을 올리고 웹사이트에 돌아온 순간부터, **분석이 진행되는 단계가 실시간으로 하나씩 채워지는** 것:
```
PR 생성됨
  ↓ (실시간)
⓪ 입력 수집 ✓ (421자)
① 개념 추출 ✓ (36ms, 개념 4개)
② KMS 검색 ... ← 지금 여기 (스피너)
③ 충분성 판단 (대기)
④ 규칙 판정 (대기)
⑤ 코멘트 생성 (대기)
```
이걸 토글로 펼쳐서, 기다리는 동안 "지금 무슨 단계를 하고 있고, 각 단계가 얼마 걸렸는지"를 실시간으로 보여준다.

### 단계적 구현 경로
- **A단계 (반나절, 먼저)**: 로딩 상태 표시
  - 프론트가 GET /review 폴링 중 `found: false`이면 "분석 중..." + 스피너
  - `found: true` 되면 완성된 trace 타임라인으로 전환
  - 실제 단계 진행은 아직 실시간 아님 — 단 "돌아가고 있다"는 건 보임
- **B단계 (1~2일, 진짜 실시간)**: SSE(Server-Sent Events)
  - m3가 각 노드 실행을 마칠 때마다 프론트로 이벤트 푸시
  - 프론트가 받아서 타임라인을 한 칸씩 실시간 채움
  - 엔드포인트: `GET /review/stream/{owner}/{repo}/{pr_number}` (SSE)
  - run_review에 노드별 콜백 추가 → 이벤트 emit

### 주의
- 계약(M3ReviewResponse) 본체는 유지, SSE는 별도 엔드포인트로 추가 (기존 polling 호환)
- m1을 경유하지 않고 프론트가 m3에 직접 연결 (현재 ReviewDetail이 m3 직접 폴링하는 구조 그대로)

## v2-2. 팀 KMS(m0) 연결

### 왜 필요한가
현재는 우리 자체 corpus/(로컬 마크다운 8규칙)를 쓴다. 팀에는 m0(문서 업로드·파싱·청킹·Neo4j/pgVector 저장) KMS 파이프라인이 따로 있다. v2에서는 **팀이 m0에 컨벤션 문서를 올리면 우리 에이전트가 그걸 검색**하는 구조로 전환한다.

### 무엇을 바꾸는가 (3포인트)
1. m0의 ChunkItem에는 `rule_id`가 없음 → 우리 검색은 rule_id 기준이므로 매핑 또는 추출 로직 필요
2. ingestion.py가 로컬 corpus 대신 m0 출력(또는 m0가 적재한 pgVector)을 읽도록 소스 전환
3. 임베딩 차원 정합 — 현재 bge-m3 1024d로 통일돼 있으므로 m0도 동일 모델이면 호환

### 전제
- m0 출력 포맷 확정, rule_id 부여 방식 팀 협의

## v2-3. 레포 풀 소스 분석 (AST·커버리지·성능)

### 왜 필요한가
원래 설계는 "PR 변경 줄 + 주변 연관 함수 전체를 AST로 끌어와 분석"이었다. 그리고 테스트 커버리지·성능 분석도 계획에 있었다. 그런데 이 셋은 **공통 전제**가 있다 — 레포 전체 소스가 디스크에 있어야 한다. 현재 m1은 PR 이벤트 시 레포를 clone하지 않고 **diff(바뀐 줄)만** m3에 넘긴다. 그래서 셋 다 비활성/스텁 상태다.

### 무엇을 하는가
- **AST 함수 컨텍스트** (코드는 이미 존재, 입력만 대기): `repo_meta["files_root"]`에 체크아웃 경로가 들어오면 자동 활성화. 변경 줄이 속한 함수 전체를 추출해 judge 입력에 보강.
- **테스트 커버리지 실측** (`/verify/tests` 현재 빈 스텁): 테스트 실행(코드 전체 + 러너 + 샌드박스) 필요.
- **성능 분석 실측** (`/analyze/performance` 현재 빈 스텁): 시간복잡도·N+1 등 정적 분석.

### 전제
- m1이 PR 시 레포 clone → `files_root`를 m3에 전달 (m1 모듈 수정 — 팀 협의)

## v2-4. corpus 규칙 확장

### 왜 필요한가
현재 8규칙. 팀이 실제로 쓰는 이슈 분류(보안·성능)를 더 넓게 커버하면 실용성이 올라간다. corpus에 마크다운 추가 + `make reindex`만으로 코드 변경 없이 확장된다 (핫스왑 구조의 이점).

### 추가 후보
- **보안**: SQL injection (✅ CONV-SQL-008 있음), clickjacking (신규 — 단 프론트 코드 대상이라 골든셋이 파이썬 전제인 현 구조와 정합 검토 필요)
- **성능**: N+1 query (✅ CONV-DB-004 있음), 시간복잡도 (신규 — O(n²) 중첩 루프 등)

### 작업
- 각 규칙: 사고 동기 + 금지 패턴 + 사내 교정 지시 작성 → corpus/*.md → reindex
- 골든셋에 해당 위반/정상 케이스 추가 (게이트1 라벨 확정)

## v2-5. KMS gap 영역 LLM 보조 분석 (2티어)

### 왜 필요한가
현재 원칙은 "KMS에 규칙이 없으면 gap 보고(지적 안 함)"다. 이게 차별점("모르면 모른다")이지만, 실용 관점에선 gap 영역을 완전히 묵살하는 게 아쉬울 수 있다.

### 목표 (2티어 구조)
- **1티어 (현행)**: KMS 근거 지적 — rule_id 인용 + string-match 보장
- **2티어 (신규)**: KMS gap일 때 LLM 보조 분석 — "KMS 규정 없음. LLM 참고 분석: O(n²) 패턴 감지(참고용)"
  - severity는 항상 Info 고정
  - "공식 규정 아님" 명시
  - DB에 `source="llm_advisory"` 플래그로 구분 저장

### 주의
- 1티어의 환각 0% 보장(string-match)이 2티어로 오염되지 않게 분리
- 추가 시 gap PR(pr_011·012) 라벨이 바뀌므로 게이트1 재확정 필요
