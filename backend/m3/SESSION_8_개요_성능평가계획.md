## 0. 선행 — 평가 전에 시스템부터 완성 (8-0)

> ★ **평가는 완성된 시스템 위에서만 의미 있다.** 지금 시스템엔 미완성 3가지가 있어, 이걸 먼저 끝낸 뒤 8A~8E를 한다.

| 미완성 | 지금 | 담당 세션 |
|---|---|---|
| **LLM 경로** | `google.generativeai`(지원종료)로 죽어 규칙기반 폴백 | **8-0a** `google.genai`로 교체·복구 |
| **탐지기 연결** | 6개 중 4개만 파이프라인 연결(TEST-003·PERF-003 미연결) | **8-0b** 6개 전체 연결 |
| **RAG** | 기본 OFF 토글(제품 목표=상시 인용과 어긋남) | **8-0c** 기본 ON(테스트는 seam으로 끔) |

→ 안 하면: 4탐지기로 평가 후 6탐지기로 바꾸면 8B 재작업, LLM 죽은 채 8C, RAG 꺼진 채 8D = 전부 무의미. **그래서 8-0(a/b/c)이 최우선.**

## 1. 왜 다시 하나 — 현재 평가의 한계 (정직한 진단)

| 층 | 지금 | 한계 | 제대로(베스트 프랙티스) |
|---|---|---|---|
| **1. 시스템 성능** | 엔드포인트 통시간 1회(verify 7.3s·perf 5.3s·review 1.5s) | 단계 내부가 블랙박스, 1회·평균만 | 단계별 워터폴 + 여러 PR + p50/p95 + 병목 식별 |
| **2. 탐지 정확도** | 골든 1건(5이슈) → recall 100%·오탐 0% | 표본 1개, 음성케이스 없음, rule별 없음 | 확장 라벨셋(양성+음성) + rule별 P/R/F1 + FP/FN 분석 |
| **3a. 코멘트 품질** | verdict·이슈개수 일치만 | "좋은 코멘트인가"는 미측정 | LLM-as-judge 루브릭 + verdict 정확도 |
| **3b. RAG 품질** | 거의 없음 | 인용의 관련성·충실도 미측정 | RAGAS(context precision/recall·faithfulness) 신규 |
| **4. 통합** | 트레이싱 일부 | 평가가 흩어짐·추적 안 됨 | LangSmith Dataset+Experiment+Evaluator |

## 2. Task 분할 (8-0 → 8A~8E) — 순서·의존·MVP

> ★ **8-0(시스템 완성)을 최우선으로 먼저 끝낸다.** 평가(8A~8E)는 완성된 시스템 위에서만 의미가 있다.
> 8-0은 **작은 세션 3개**로 쪼갰다(각각 돌려보고 확인 후 다음): 8-0a LLM복구 → 8-0b 6탐지기연결 → 8-0c RAG상시ON.
> 이로써 8C의 SDK 교체·8D의 RAG 켜기 선행이 **8-0으로 흡수**된다.

```
8-0a LLM 복구(SDK 교체)       ─ ★최우선 1. google.generativeai→google.genai (8-0b가 의존)
8-0b 6탐지기 연결             ─ ★최우선 2. 선행: 8-0a. TEST-003·PERF-003 → main.run() (8B가 의존)
8-0c RAG 상시 ON             ─ ★최우선 3. 독립(순서 무관). 기본 ON + HF캐시볼륨 (8D가 의존)
8A 시스템 성능(단계별 계측)   ─ 선행: 8-0b (6탐지기·RAG ON 기준으로 측정)
8B 탐지 정확도(벤치마크 확장) ─ 선행: 8-0b (골든라벨을 6탐지기 기준으로)
8C 코멘트 품질(LLM 판정)      ─ 선행: 8-0a (SDK 이미 교체됨 → 품질 채점만)
8D RAG 품질(RAGAS 신규)       ─ 선행: 8-0c (RAG 이미 ON) + chunks 접속
8E LangSmith 통합             ─ 선행: 8B/8C/8D 평가셋 존재
```

| 세션 | 한 줄 목표 | 새 의존성 | MVP 합격선 |
|---|---|---|---|
| **8-0a** | LLM 경로 복구(SDK 교체) | (`google.genai`) | refine 이 실 LLM 한 줄 반환(폴백 아님) + 회귀 0 |
| **8-0b** | TEST-003·PERF-003 파이프라인 연결 | 없음 | 6탐지기 스모크 동작 + 결정성 택일 기록 + 회귀 0 |
| **8-0c** | RAG 기본 ON + HF캐시볼륨 | 없음 | 실행 기본 ON·테스트 seam off + 재다운로드 제거 + 회귀 0 |
| **8A** | 단계별 시간 워터폴 + p50/p95 + 병목 | 없음(기존 `@instrument` 수확) | 단계 시간표(6탐지기·RAG 포함) + ≥5 PR + 병목 1개 명시 |
| **8B** | rule별 Precision/Recall/F1 | 없음(eval.py 확장) | 라벨 PR ≥5(양성+음성) + **6탐지기** rule별 P/R/F1 표 |
| **8C** | "왜 한 줄" LLM-judge + verdict 정확도 | 없음(SDK는 8-0에서 교체됨) | 판정 일치율 + why 루브릭 점수 ≥10건 |
| **8D** | RAG 인용 RAGAS 점수 | `ragas` | 평가셋 ≥10건 + context precision/recall·faithfulness |
| **8E** | 위 셋을 LangSmith로 묶고 회귀추적 | (LangSmith 키) | dataset+experiment+evaluator가 대시보드에 보임 |

## 3. 공통 원칙 (모든 8x 세션 공통 — 어기지 말 것)

- **평가 전 구현 점검(0단계) ★**: 각 세션은 점수를 내기 전에 **대상 코드가 멀쩡한지 먼저 확인** — 그 영역 기존 테스트 green + 알려진 입력 스모크 1회. 버그·미구현이면 멈추고 보고(또는 작은 것만 고치고 기록). **깨진 코드 위에서 숫자를 내면 그 평가는 거짓이 된다.**
- **정직성(가짜 금지)**: 측정 못 한 값은 빈칸/생략. 가짜 숫자·가짜 라벨·가짜 인용 금지. m3 전역 1원칙.
- **TDD**: 각 세션은 `superpowers:test-driven-development` 스킬로 — 평가 코드도 테스트 먼저.
- **재현 가능**: 같은 입력=같은 결과. 평가 스크립트는 `validation/`(또는 `bench/`)에 두고 1커맨드로 재실행.
- **데모≠실측 오염 금지**: 평가는 fixture/라벨셋 기준. 실 GitHub 게시·실 DB 쓰기 없이 도는 경로를 우선.
- **결과는 표로**: 각 세션 끝에 [지표 표 / 표본 수 / 합격여부 / 한계] 정리.
